# Motion Tuner · 产品愿景与价值定位

> 这份文档沉淀 Motion Tuner 作为独立项目的深层思考——产品哲学、价值判断、竞争定位、叙事框架。
> 用于后续写宣传文案、产品文章、融资材料时取材。
> 不是技术文档，不是 API 参考，不是代码规范。

---

## 一、一句话定位

> Motion Tuner 是生产环境里的 AI 协作调参协议：把设计师的"感觉"直接变成代码参数，消除动效从设计到开发之间的翻译损耗。

口号：**感觉即代码。**

---

## 二、Motion Tuner 解决的核心问题

### 问题本质

动效一旦复杂到超过自然语言可精确描述的临界点，设计师和开发/AI 之间就会出现严重翻译损耗。

传统链路：
```
设计师脑中的感觉
  → 录屏 / 文字 / 口头描述
  → 开发猜参数
  → 实现
  → 设计师验收
  → "不对，再快一点 / 再轻一点 / 节奏不对"
  → 继续猜
```

真正痛的不是开发不会写动画，而是**"感觉"没有被转成可操作、可同步、可复用的参数**。

### Motion Tuner 的链路

```
设计师感觉
  → 直接在真实产品/预览环境里调
  → 感觉旋钮驱动底层参数
  → 实时 preview
  → 复制 AI 友好的 TS patch
  → AI 改代码
  → 上线/提交
```

**"感觉 → 参数 → 代码"之间的转换损耗被消除了。**

---

## 三、价值阈值：不是所有动效都需要

这个边界非常重要，它避免了产品陷入"所有东西都要可视化调参"的臃肿。

### 适合 Motion Tuner 的

- 多参数耦合动效（翻牌 stagger + 翻转次数 + 末段减速 + 音效节奏...）
- 多状态转场（default → hover → active → loading...）
- 复杂节奏控制（前快后慢、惯性、过冲、弹性...）
- 动态品牌表达（品牌动效 DNA、情绪传达）
- Agent 状态表达（AI 正在思考、多任务切换、响应反馈...）
- 高级交互反馈（翻牌、粒子、流体、3D 旋转...）
- 设计师说不清但能感受到"不对"的部分

### 不需要 Motion Tuner 的

- 简单 hover 上浮
- 简单 fade in/out
- 简单位移动画
- 两个参数就能说清的动效——嘴说就行

**判断标准：如果两句话能描述清楚，就不需要 Motion Tuner。**

## 四、核心产品哲学

### 哲学 1 · 封装复杂度，不是暴露复杂度

AE、Rive、甚至很多开发调参工具的做法是：把底层能力暴露给专业人士。

Motion Tuner 的做法是：把底层复杂度交给 AI 和系统，把用户能感知的"感觉维度"暴露出来。

```
不要让用户调：
  duration = 420
  easing = cubic-bezier(0.16, 1, 0.3, 1)
  staggerDelay = 0.08
  rotateXFactor = 0.35
  scaleFactor = 0.04
  springDamping = 0.65

而是让用户调：
  更轻 / 更重
  更快 / 更慢
  更弹 / 更稳
  悬浮更强 / 更弱
  节奏更紧 / 更松
  翻转更利落 / 更柔和
```

**设计原则：专业能力 AI 化，不等于把专业工具简化成玩具；而是把专业参数重新映射成用户可感知的控制维度。**

### 哲学 2 · 临时脚手架，不是永久 UI

Motion Tuner 不是 Storybook，不是 playground，不是永久 UI。

它是嵌入生产代码里的临时调参层：

```
真实产品/预览环境里调
  → 直接产生 AI 能理解的 patch
  → AI 改代码
  → 面板移除
  → 产品干干净净
```

**Motion Tuner 的本质不是"动效编辑器"，而是"生产环境里的 AI 协作调参协议"。**

它的价值不是面板本身，而是它建立了一种协作方式：
- 设计师不用懂代码
- 开发不用反复猜感觉
- AI 能拿到结构化参数
- 产品/老板也能参与体验微调
- 最终代码不被调参 UI 污染

### 哲学 3 · 感觉旋钮优先

"感觉旋钮"是 Motion Tuner 区别于所有通用调参工具的核心差异。

一根"悬浮强度"滑杆，背后同时驱动 Y 位移、scale、阴影模糊、阴影深度——但设计师看到的只是"悬浮感"的强弱。

好的 schema 设计 = 用最少的感觉旋钮覆盖 80% 的调参需求，剩下 20% 才打开 advanced。

**如果一个 schema 里没有归一化的感觉旋钮——不是 SDK 的问题，是接入方还没设计完。**

## 五、与同类工具的差异

| 维度 | Storybook / Theme UI | Rive / AE | Motion Tuner |
|------|---------------------|-----------|-------------|
| 在哪调 | 独立沙箱 | 独立专业软件 | **生产代码里** |
| 调完怎么办 | 手动同步回代码 | 导出资产再集成 | **点复制给 AI** |
| 暴露什么参数 | 所有 props | 所有时间轴参数 | **感觉旋钮** |
| 面板生命周期 | 永久存在 | 永久存在 | **临时脚手架** |
| 谁能用 | 开发 | 动效专家 | **设计师/产品/AI/开发** |
| 学习成本 | 低-中 | 高 | **极低**（拖滑杆） |

## 六、0→70→100 分的精度阶梯

AI 时代的创作流程正在发生结构性变化：

```
0 → 70 分：
  自然语言生成很高效
  通用 AI / 生成式工具很适合
  "帮我做一个翻牌效果的标题"→ AI 秒出

70 → 85 分：
  需要结合专业上下文、局部选择、设计系统
  通用 AI 开始力不从心
  "翻牌再快一点"→ AI 改了但不确定改对没

85 → 100 分：
  自然语言描述成本指数级上升
  "这个节奏不对""再轻一点但不要慢""前半段快后半段稳"
  必须用可视化、参数化、交互式方式精调
  Motion Tuner 的核心价值区间
```

**Motion Tuner 不是 0→1 的工具，是 85→100 的工具。**

## 七、多角色协作视角

### 设计师
调感觉旋钮，不调底层数学。切状态看不同场景下的表现。调到满意，点复制。

### AI
收到 copy 的 TS patch（带 target id + key/value + 注释），grep 定位 schema，改 defaultConfig，提交。

### 开发
定义 schema（哪些参数暴露、如何分组）。接入 `useMotionTuner`。验证可拆除性。日常几乎不介入参数调整——如果 schema 定义得好的话。

### 产品/老板
也可以打开面板调调看，不需要懂代码。"我觉得这个翻牌太快了"→ 自己拖一下 → "就这个感觉" → 复制给 AI。

## 八、为什么 demo 用翻牌和球

这不是为了好看——是为了**证明 Motion Tuner 存在的合理性**。

| 动效 | 嘴能说清吗？ | 嘴说不清的维度 |
|------|------------|--------------|
| 翻牌大字 | 不能 | 翻几次、第几次开始定、每个字 stagger 多少、临界过冲、落定节奏... 至少 10 个维度耦合 |
| ASCII 球转动 | 不能 | 转速 X/Y/Z 三轴、字符密度、depth-alpha 曲线、字符集、半径占比... |
| 普通 hover 上浮 | 能 | "上移 4px"——不需要 Motion Tuner |

**demo 的动效必须是"嘴说不清"的那种，否则演示完用户一句"我跟 AI 说一下"就把产品价值否决了。**

## 九、产品叙事框架（写文章用）

### 核心叙事线

```
AI 能快速生成动效 Demo
  ↓
但 Demo 从"能跑"到"好用、好看、舒服、有质感"
  仍然需要精细调优
  ↓
动效进入深水区后，自然语言的精度不够
  "再快一点""感觉不对"说了 30 秒开发还是不确定
  ↓
Motion Tuner：把感觉变成可操作的参数
  在真实产品里调 → 实时 preview → 复制给 AI → 代码即更新
  ↓
感觉即代码。
```

### 差异化定位句

> Motion Tuner 不是让你做出动效，而是让你把 AI 做出的动效调到真正满意。

> AI coding 工具可以生成 Demo。但生成之后，Demo 的动效、节奏、体验细节怎么调？Motion Tuner 是 AI coding 之后的体验精修层。

### 竞品对比叙事

> Storybook 让开发者在沙箱里调参。Rive 让动效专家做时间轴动画。Motion Tuner 让设计师在真实产品上拖一根"感觉旋钮"——调完复制，AI 改代码，面板消失。

## 十一、动效为什么不是附属功能

动效不是"好看一点"的装饰层。在 AI 产品、Agent 产品、复杂交互产品里，动效本身就是**体验质量**的一部分：

- 状态变化怎么过渡——让用户理解"发生了什么"
- Agent 正在思考怎么表达——让用户有信任感和耐心
- 多任务切换怎么有连续性——让用户不丢失上下文
- Hover、展开、折叠、翻牌、加载、成功、失败如何反馈——控制感
- 复杂信息如何通过动态节奏降低认知负担——可理解性

**这些不是"美化"问题，是体验的可理解性、信任感和控制感的问题。**

所以 Motion Tuner 服务的不只是"让动效好看"，是"让动效准确传达设计意图"。

## 十二、与 AI coding 工具的关系

### 不是竞争，是协作

AI coding 工具（v0 / Lovable / Bolt / Cursor）可以快速生成可运行 Demo。

**但生成之后呢？**

Demo 的动效、节奏、体验细节怎么调？

- 在 v0 里说"这个翻牌再快一点"→ 可能改对，也可能改偏，多轮对话后精度递减
- 用 Motion Tuner → 打开面板，拖一根"翻牌速度"滑杆，松手即看效果，10 秒搞定

**Motion Tuner 是 AI coding 之后的体验精修层。**

### 精度阶梯的详细拆解

```
0 → 70 分：
  AI coding 极其高效
  "帮我做一个翻牌效果" → 秒出
  这阶段不需要 Motion Tuner

70 → 85 分：
  几轮对话能推进
  "翻牌再快一点" → AI 改了，大概率方向对
  Motion Tuner 开始有价值（但不是必须）

85 → 100 分：
  自然语言成本指数级上升
  "前半段快后半段稳""翻的时候有惯性但别弹""这个球旋转要更有空间感"
  你可能说了 30 秒，开发/AI 还是不确定你到底要什么
  这阶段 Motion Tuner 的价值最大——因为它把不可言传的感觉变成可操作的旋钮
```

**关键认知**：70→80 分可能只要几轮对话（边际成本低），但 80→100 分可能需要几十轮（边际成本指数增长）。Motion Tuner 消灭的是后半段的指数增长。

---

## 十三、AI 是协作者，不是决策者

这条哲学贯穿 Motion Tuner 的所有交互设计：

- **AI 再自信，也不是用户肚子里的蛔虫**
- AI 的价值是**扩展可能性**，不是替用户做决定
- 生成方案 → 多方案对比，让用户选
- 调整参数 → 给感觉旋钮，让用户调
- 给建议 → 不替用户拍板

**实践原则**：
- Motion Tuner 的面板永远是"让用户做最后判断"的工具
- AI 可以推荐参数范围、生成 schema、分析调整趋势
- 但**拍板权在用户手里**——滑杆的终态是用户松手那一刻的值

## 十四、叙事指南（写文章时用）

### 主线结构（不要散）

写宣传材料时有一个风险：Motion Tuner 同时涉及"调参面板 / AI 协作 / 感觉旋钮 / 可拆除 / 多 target"很多概念，容易变成功能列举，失去叙事力量。

**正确的主线**不是并列，是递进：

```
AI 能快速生成动效
  ↓
但通用 AI 难以完成精细调优（自然语言在深水区精度不够）
  ↓
Motion Tuner 让感觉变成可操作的参数
  ↓
感觉旋钮 → 实时 preview → 复制给 AI → 代码即更新
  ↓
感觉即代码。
```

**错误的结构**（会散）：
```
Motion Tuner 可以调参
Motion Tuner 也支持多状态
Motion Tuner 还能复制代码
Motion Tuner 还是可拆除的
```

### 核心对比句式

以下句式在写文案时有高转化率（用"不是X，是Y"制造认知冲突）：

- 不是暴露复杂度，是封装复杂度
- 不是动效编辑器，是 AI 协作调参协议
- 不是永久 UI，是临时脚手架
- 不是独立沙箱，是嵌入生产环境
- 不是让你做动效，是让你把 AI 做出的动效调到满意
